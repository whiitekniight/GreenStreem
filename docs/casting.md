# Casting

While a channel, movie, episode or recording is playing, tap **Cast** (the standard screen-and-waves icon), then select a TV from the single device list. Approve the TV's normal permission prompt if it displays one.

No GreenStreem receiver app mode, setup page, pairing code or protocol selection is used. Google Cast and DLNA renderers are discovered together on the home network; duplicate devices are filtered when their address/name matches. Both phone/tablet and TV must be reachable on the same network. TVs/sticks without a compatible built-in casting receiver will not appear. iOS and AirPlay are outside this change.

Google Cast uses Google's Default Media Receiver. The sender initializes Google services only when opening the Cast picker and only if Play services is available. Devices without Play services can still discover DLNA renderers. The pinned Cast framework version is 22.3.1: 23.0.0 ships Kotlin 2.4 metadata that the project's current Kotlin compiler cannot consume.

For H.264 live TV delivered as MPEG-TS, the phone prepares a temporary compatibility stream. Our adapter uses the existing Media3 extractor and FFmpeg audio decoder, Android's AAC encoder, and our own MPEG-TS packet writer. Video is copied without re-encoding; audio is encoded to AAC, with multichannel audio downmixed to stereo. Google Cast receives an HLS playlist; DLNA receives a continuous HTTP MPEG stream. No LibVLC or additional conversion dependency is added. Other sources retain their direct playback path. Direct MPEG-TS file playback is not accepted by every Google Cast receiver; the test Shield rejected the raw TS fixture and accepted its MP4 equivalent. Native TV format support applies to saved recordings. The picker and controls explicitly use an AppCompat dialog theme because MainActivity itself uses a Leanback theme; relying on its host theme caused a live-TV-only crash during verification.

Compatible movies normally play directly on the TV. Live compatibility streams require the phone to remain connected. Saved recordings use a temporary, read-only URL for the one selected file; storage credentials stay on the phone/tablet. Keep that phone/tablet on Wi-Fi with the recording storage connected while casting a saved recording. Its ongoing notification can stop sharing the file. The temporary URL is revoked when sharing stops or the service is destroyed; no folder listing or recording deletion API is exposed. Nothing is made internet-facing by configuring router forwarding.

The phone's player pauses only after the TV reports playback has started. If a stream/container/codec is unsupported, an error is shown and local playback remains available. Casting starts without opening a controls dialog. Tap the phone video or Cast icon to show Play/pause, Stop casting and Change TV; seek controls are omitted for live TV. The receiving TV's native codec and provider/network restrictions still apply; H.264 live TS audio is converted as described above; other unsupported video codecs are reported rather than silently claimed compatible.

The shared button/category styles use dark interiors with colored outlines. Playback buttons have fixed minimum touch widths, explicit gaps, and a horizontally scrollable row so labels do not run together. Existing EPG cursor and movie seeking logic are unchanged.

Physical checks (2026-11-26): live US REELZ played from the Samsung phone to testing Shield 192.168.1.160 through the native Google Cast receiver (screenshot `output/casting-shield-live-working.png`). Samsung TU7000 192.168.1.70 also reported PLAYING/OK with its position advancing beyond 34 seconds using the phone's live compatibility stream (`output/casting-samsung-live-working.json`). A segment produced by the phone independently decoded without errors as H.264 1280x720 video and AAC 48 kHz stereo (`output/casting-phone-live-proof.json`). The user confirmed both Samsung picture and sound work.

Samsung initially rejected our continuous stream because NanoHTTPD emits `Content-Length: -1` on HEAD for unknown-length bodies. The rejection was independently reproduced with a controlled fixture: invalid HEAD produced UPnP 716/701 and STOPPED; valid chunked HEAD allowed PLAYING and advancing position. `CastHttpResponse.live` fixes the response without inventing a finite file size. Its regression check verifies both HEAD headers and a complete GET body. Twenty-one JVM checks passed, covering this exchange, TS program-table CRCs, packet payload preservation and continuity counters, plus existing casting/guide/recording checks. Casting is included in customer release 1.9.68.

Final physical verification (2026-11-26): the Shield's longer run initially stalled around 14 seconds because the presentation-only extractor API discarded original video decode timestamps for reordered H.264 frames. `CastTransportClock` retains the original PES PTS/DTS mapping as network data enters the extractor, including fragmented reads and 33-bit wrap. The TS writer now emits the preserved DTS/PCR, and parameter sets are prepended to the keyframe in the same PES. The corrected Shield stream remained PLAYING past 103 seconds through multiple sliding-window updates; remote pause/resume was verified (`output/casting-shield-progress.json`). Switching from Shield to Samsung succeeded and Samsung reported PLAYING/OK. Its Stop casting button was verified to produce STOPPED and shut down the relay service. The front-room Shield at 192.168.1.192 was never selected.

Casting starts with no controls popup. Tapping the fullscreen phone video opens Play/pause, Stop casting and Change TV. Controls also remain available after returning from the phone home screen; active target/media state survives activity recreation without retaining an Activity or callback. New DLNA loads stop the previous transport resource before setting and playing the new URI, avoiding Samsung's transition rejection. Twenty-four JVM checks passed after these changes. Customer release 1.9.68 includes this casting path and the automatic local/USB storage fallback described in recording-storage.md.
